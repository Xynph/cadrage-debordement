# Recette SDK du suivi de d83a817

La première tête diagnostique conservait la production et la géométrie reçues dans la PR 566. Elle a révélé une vraie régression P1 : aux bornes des listes Fatigue et Individuel, la molette faisait défiler le nouveau ContextualPageWorkspace de16px et déplaçait l’en-tête. Le suivi corrige maintenant ces trois lignes de director.gd : les ScrollContainer internes préexistants refusent le passage forcé de molette et utilisent MOUSE_FILTER_STOP ; le wrapper extérieur, créé ensuite, conserve son défilement hors des listes. Ce correctif est une correction produit P1, pas la suppression d’un test obsolète. Elle réunit les corrections de recettes supplémentaires, dont les trois familles 567, 568 et 569. Aucun push n'est effectué sur la branche commune d83a817 déjà verte.

Le workflow SDK enregistré offre un dispatch `scope=followup` : il installe le même SDK officiel épinglé, effectue le même staging/import strict puis exécute, en trois groupes sur trois runners publics isolés, le manifeste explicite `ci/godot-sdk-followup.json`. Le contrôleur existant, ses refus SKIP/ERROR/ANSI et sa borne de 180 secondes par suite/cas sont conservés. Les 16 tests du contrôleur sont des unités VM ; ils ne constituent pas un reçu Godot.

Les événements PR/push normaux et le dispatch `scope=full` conservent le job sdk antérieur, matrices P1 incluses, et exécutent également les trois groupes de nouveaux cas. Les groupes sont une partition validée du manifeste : aucune omission ni duplication de suite. Chaque runner reste séquentiel avec son propre SDK/profil ; le contrôleur des suites n’est pas redéveloppé. Le dispatch explicite followup avait omis P1 tant que les sources de production étaient inchangées. Après le correctif produit de molette, la recette finale utilise scope=full : le job sdk rejoue les12 suites historiques et toutes les matrices P1, en parallèle des trois groupes de36 nouveaux cas. Les reçus d83 et de la première tête561 gardent leur portée propre ; aucun ancien reçu P1 n’est réattribué au nouveau fichier.

La possibilité de dispatch hors main sera éprouvée par un unique POST sur la branche figée : s'il est accepté, il lance directement la recette utile. Si GitHub refuse parce que le workflow est absent de la branche par défaut, le repli est une PR brouillon vers main avec ses contrôles habituels, sans changement des paramètres GitHub ni de la politique de sélection. Runner Ubuntu standard public, aucun service payant, aucun cache/artifact upload ni nouvelle Release.

La liste finale ne reçoit que des suites/cas qualifiés et leurs sources exactes. Un résultat rouge ou un cas encore incomplet n'est pas renommé PASS ; les réparations sont poursuivies dans les mêmes familles.
